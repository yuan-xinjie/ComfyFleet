# ComfyFleet · 技术评估（Tauri 版）

> 评估对象：类 ComfyUI Desktop 的 Windows 桌面启动器，额外支持多实例、环境诊断、版本治理、节点治理。
> 依据：`Comfy-Org/desktop` v0.9.x、`comfyanonymous/ComfyUI` 的 `comfy/cli_args.py`、`Comfy-Org/ComfyUI-Manager` 的 `cm-cli` 与数据文件、PyPI `torch-directml` 元数据，均核对原文。
> 修订：2026-10-28（按已确认决策改为 Tauri + 开源；同日 **放弃 DirectML**，见 §0.1 决策表）

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 能不能做 | **能做**，17 项需求全部有官方机制，无死路 |

## 2. 官方实现事实（设计依据）

### 2.1 ComfyUI Desktop（`Comfy-Org/desktop`）

- 栈：Electron 31.3.1 + TS + `node-pty` + `electron-store` + `wait-on` + `systeminformation`；electron-builder / todesktop；**GPL-3.0**。
- **uv 随包内置**（`assets/uv/win/uv.exe`，锁 `uvVersion: 0.8.13`）；ComfyUI 版本锁 `config.comfyUI.version`；Manager 锁 **commit**。
- 目录：venv 在 `<base>/.venv`，uv 缓存在 `<base>/uv-cache`，解释器 `.venv/Scripts/python.exe`。
- 安装顺序：`uv venv --python <ver> --python-preference only-managed` → `ensurepip` → `uv pip install -r requirements.compiled`（`--index-strategy unsafe-best-match`）→ 失败回退先装 torch 三元组、再 core requirements、再 Manager requirements。
- **依赖自检官方做法**：`uv pip install --dry-run -r requirements.txt`，输出含 `Would make no changes` 即完整；否则解析 `Would install N packages`。
- **导入自检**：`yaml, torch, uv, toml, numpy, PIL, sqlalchemy`。
- 启动参数：`--user-directory --input-directory --output-directory --front-end-root --base-directory --database-url --extra-model-paths-config --log-stdout`；默认 `127.0.0.1:8000 --enable-manager`。
- 就绪：`wait-on /queue`，1 s 间隔，**30 min 上限**；停止 10 s 超时。
- 环境变量：`VIRTUAL_ENV`、`PYTHONIOENCODING=utf8`。
- **不做**：多实例、节点版本切换、依赖冲突解释、git 版本治理。

### 2.2 ComfyUI 核心（`comfy/cli_args.py`）

`--listen`（nargs="?"，无参 = `0.0.0.0,::`）、`--port`、`--enable-cors-header`、`--tls-keyfile/--tls-certfile`、`--base-directory`、`--models-directory`、`--output-directory`、`--user-directory`、`--database-url`、`--extra-model-paths-config`（可多次）、`--disable-all-custom-nodes` + `--whitelist-custom-nodes` + `--disabled-nodes-config`、`--offline`、`--enable-manager`、`--cpu`、**`--directml [N]`**、`--cuda-device`、`--verbose`、`--log-stdout`（默认写 **stderr**）、`--front-end-version/--front-end-root`。

### 2.3 ComfyUI-Manager

- `cm-cli.py` V2.24：`install/reinstall/uninstall/update/disable/enable/fix`、`show|simple-show [installed|enabled|disabled|not-installed|all|snapshot|snapshot-list]`、`save-snapshot/restore-snapshot`、`restore-dependencies`、`cli-only-mode`、`clear`；需同环境 + `COMFYUI_PATH`；`--channel`/`--mode`。
- 数据文件（需缓存）：`custom-node-list.json`（3.0 MB）、`extension-node-map.json`（2.5 MB）、`github-stats.json`（1.0 MB，**含更新日期与 star**）、`model-list.json`、`alter-list.json`、`pip_overrides.json.template`、`node_db/`、`snapshots/`。
- `pip_overrides.json` = Manager 自己的"强制版本覆盖"机制 → 我们的依赖修复可复用同一思路。

### 2.4 DirectML 的真实状态（**已放弃**，保留为决策记录）

> 本节已完成使命：正因为下面这些约束，2026-10-28 决定不实现 DML 引擎。内容仅作历史参考，不再作为实现依据。

| 事实 | 值 |
|---|---|
| 最新版 | `0.2.5.dev240914`，**上传于 2024-09-15**（已约 2 年无新版） |
| 硬依赖 | `torch==2.4.1`、`torchvision==0.19.1`（**精确 pin**，无法协商） |
| 轮子 | cp38–cp312（Windows `win_amd64` 与 manylinux） |
| 状态/许可 | `Development Status :: 3 - Alpha`；MIT |
| ComfyUI 侧 | `--directml [N]` 走 `torch_directml.device()` |

**推论**：DML 实例必须锁 Python 3.12 + torch 2.4.1 全家桶。这带来三个硬后果：

1. **与最新 ComfyUI 可能不兼容**（torch 2.4.1 是 2024 年中版本，核心代码可能用到更新的 torch API）→ 必须为 DML 维护一个"已验证 ComfyUI 版本区间"，M1 期间实测确定。
2. **节点兼容性差**：DirectML 算子覆盖不全，未覆盖算子回退 CPU；`xformers/sage/flash-attn` 全部不可用。部分节点直接报 `not implemented for 'PrivateUse1'`。
3. **升级路径被上游卡死**：除非微软发新版，DML 实例永远停在 torch 2.4.1。产品上应明示"DML 为兼容性优先的遗产通道"，并**默认不选**。

### 2.5 torch 索引的真实状态（实测，2026-10-28）

直接抓 `download.pytorch.org` 各索引的 win_amd64 文件列表得到：

| 索引 | 最新 torch | 可用 cp 标签 | 结论 |
|---|---|---|---|
| `cu130` | **2.14.1** | cp310 – cp315 | 唯一持续更新的 CUDA 索引 |
| `cu129` | **2.9.0** | cp310 – cp314 | **已停更**，只能用老 torch |
| `cu128` | 2.11.0 | — | 同样停在旧版本 |
| `cpu` | 2.14.1 | cp310 – cp315 | 与 cu130 同步 |

**推论（直接决定矩阵设计）**：引擎矩阵必须**按引擎分别记录 torch 版本**。用一个全局版本号，cu129 就会去装 2.14.1，然后必然失败。
另外 `torchvision` 在 cu130 已到 0.29.1（对应 torch 2.14.x），因此矩阵只 pin `torch`，让解析器按 `torchvision` 自带的 `Requires-Dist: torch==x.y.z` 匹配三元组，避免手工维护版本对照表。

## 3. 三个半真正的难点

### 3.1 "自动解决依赖冲突"不可判定（必须改产品承诺）

1. pip/uv 解析是 NP-hard，无解时不存在"正确解"。
2. 节点冲突真实存在：`numpy<2` vs `>=2`、`torch==2.1` vs `==2.9`、`transformers` 上下限互斥。
3. `install.py` 是任意代码，静态无法判定它会 pip install 什么。
4. torch 有 ABI 约束：`cpXY` + CUDA tag + torchvision 配套，错配即 `DLL load failed`。

→ 产品只承诺 5 个**可判定**动作：**检测 / 解释 / 预演 / 修复（5 选 1）/ 回滚**。文案：**"依赖体检 · 冲突解释 · 一键修复 · 可回滚"**，不写"自动解决"。

### 3.2 磁盘与显存

- 磁盘：单实例 ComfyUI 0.3 GB + venv（torch 5–9 GB）+ 模型。缓解：共享 uv cache（hardlink，同卷近零成本）、共享 models 根（默认不复制）、"克隆实例"复制 freeze 而非目录。
- 显存：双实例跑 Flux 必 OOM。缓解：启动前读显存、互斥组、一键"停 A 起 B"。

### 3.3 安全边界

- **装节点 = 执行任意代码**：显式确认 + 默认不自动跑 `install.py` + arg 数组（绝不 `shell: true`）+ git URL 校验 + 路径必须落在实例根内 + 审计日志。
- **开放远程 = 无鉴权**：`--listen 0.0.0.0` 任何能访问端口者可提交工作流 → 常驻"已暴露"标识 + 建议反代鉴权。

### 3.4 DirectML 曾是"遗产引擎通道"（**已放弃**）

> 保留分析以备上游将来解禁时复用。

`torch-directml` 锁死 torch 2.4.1，意味着 DML 实例**不能跟随 ComfyUI 主线升级**。设计上把它当作独立档位：
- 引擎矩阵里带 `warnings[]`、`comfyRange`、`constraints`（如 `numpy<2.3`）；
- UI 上标灰 + "兼容性优先"标签，默认不选；
- 检测层新增规则：**DML 实例的 torch 必须是 2.4.1**，否则 `blocker`；节点 import 失败时优先归因"算子不支持"而非"缺依赖"。

## 4. 环境检测方案（核心子系统）

### 4.1 六层模型

| 层 | 检查内容 | 实现 | 离线 | 目标耗时 |
|---|---|---|---|---|
| **L0 环境健康** | 实例根 / `.venv/pyvenv.cfg` / 解释器版本 / uv·git 可用 / 磁盘余量 / 端口占用 / 非 ASCII 或超长路径 | 纯 fs + `--version` | ✅ | < 1 s |
| **L1 核心依赖** | 该 commit 的 `requirements.txt` 是否满足；`comfyui-frontend-package` 版本匹配 | `uv pip list --format=json` + 静态比对；dry-run 兜底 | 半 | 2–8 s |
| **L2 节点依赖（静态）** | `custom_nodes/*` 的 `requirements.txt` / `pyproject.toml` / `install.py` 里的 pip 调用 | 正则 + Python `ast`（best effort） | ✅ | 1–3 s |
| **L3 解析级裁决** | 合并 L1+L2 约束求可满足解；`uv pip check` | `uv pip install --dry-run` + `uv pip check` | ❌ | 10–30 s |
| **L4 运行时** | import 冒烟；torch 三元组一致；CUDA tag 与引擎档匹配；`cuda.is_available()` 符合预期 | 实例 venv 内跑 `_probe.py` | ✅ | 2–5 s |
| **L5 启动验证** | 能否就绪；失败时 stderr 分类 | 轮询 `/queue`；错误模式匹配 | 半 | 到就绪 |

### 4.2 冲突判定规则

| 规则 | 判定 | 级别 |
|---|---|---|
| R1 | 两节点对同一 dist 的 specifier 交集为空 | `conflict` blocker |
| R2 | 已装版本不满足某节点 specifier | `unsatisfied` warn/blocker |
| R3 | 节点要求 dist 未安装 | `missing` warn |
| R4 | dry-run 显示将移除/降级被其他节点依赖的包 | `risky` warn |
| R5 | torch 三元组不配套，或 cuda tag 与引擎不符 | `blocker` |
| R6 | 节点目录在但 import 失败（依赖已满足） | `broken` warn |
| R7 | 解释器 `cpXY` 与 torch wheel 不兼容 | `blocker` |
| R8 | 前端包版本与 ComfyUI commit 期望不一致 | `warn` |
| **R9** | ~~DML 实例 torch ≠ 2.4.1~~ | 规则作废（已放弃 DML）；改为通用规则：**torch 主版本与引擎档声明的范围不符** → `warn` |

### 4.3 报告模型

```jsonc
{
  "schemaVersion": 1, "instanceId": "inst_7f3a", "generatedAt": "2026-10-28T03:20:11Z",
  "context": { "comfyCommit": "a1b2c3d", "engine": "nvidia-cu130", "python": "3.12.11" },
  "summary": { "blockers": 2, "warns": 5, "infos": 9, "durationMs": 8421 },
  "findings": [{
    "id": "f_001", "layer": "L3", "rule": "R1", "level": "blocker", "code": "SPEC_CONFLICT",
    "subject": "numpy", "expected": "<2.0 vs >=2.1", "actual": "2.2.4",
    "sources": ["node:ComfyUI-Impact-Pack/requirements.txt:3", "node:ComfyUI-Foo/requirements.txt:1"],
    "evidence": ["uv pip install --dry-run 输出第 7-12 行…"],
    "fixes": ["pin", "disableNode"]
  }]
}
```

### 4.4 实现要点

1. **探测脚本只依赖 stdlib**（`importlib.metadata` + `json`）；`packaging` 以 vendored 目录随包分发，`PYTHONPATH` 注入 → 不污染实例环境、不额外建 venv、不需联网。
2. 元数据统一 `uv pip list --format=json --color never`（比 pip 快）。
3. **uv 的裁决信息写在 stderr**（实测：`Resolved 1 package` / `Would install 1 package` / `Would make no changes` 全在 stderr）。所有 dry-run 解析必须**合并 stdout+stderr** 再匹配，否则永远拿不到结论。实测输出样例：
   - 空环境：`Would download 1 package` → `Would install 1 package` → `+ numpy==2.5.4`
   - 已满足：`Audited 1 package` → `Would make no changes`
4. **dry-run 解析必须容错**：JSON → 文本正则 → 版本探测；失败降级"静态比对"并标 `confidence: low`，绝不崩。
4. 缓存 key = `(commit, freezeDigest, nodesDigest, engine, python)`；L3 联网检查可关。
5. 性能预算：离线 L0+L1+L2+L4 < 8 s；含网络 L3 < 30 s。
6. **修复必须预演**（`+3/-1/~2` diff）→ 快照（freeze + constraints + 节点 commit）→ 执行 → 复检 → 失败自动回滚。
7. 可导出诊断包（`env.json` + `freeze.txt` + `findings.json` + 日志 + 系统信息）。
8. 不做静默修复。

## 5. 技术栈（Tauri）

| 层 | 选择 | 说明 |
|---|---|---|
| 壳 | **Tauri 2.12 + Rust 2021** | 安装包 ~10–15 MB、内存低；需 WebView2（Win11 自带，Win10 安装器 bootstrap） |
| 后端 | `tauri` + `tauri-plugin-{opener,single-instance,log}` | 自定义 `#[tauri::command]` + `tauri::ipc::Channel<T>` 做流式输出 |
| PTY | **`portable-pty` 0.9**（wezterm） | Windows 走 ConPTY；这正是 Spike S2 要验证的点 |
| 进程 | `std::process::Command` + `windows` crate（Job Object） | Windows 进程树强杀不能用 `kill()` |
| HTTP | `reqwest`（rustls） | `/queue` 就绪探测 |
| 状态 | `parking_lot::RwLock` + `serde` 持久化 | 无数据库，JSON 原子写 |
| 前端 | **React 19 + TS + Vite 7** + `@xterm/xterm` + `@tauri-apps/api` | 状态管理 v1 用轻量 Context/Zustand，先不引 TanStack Query |
| 打包 | `tauri-cli` + NSIS | 后续签名；`externalBin`/`resources` 放 uv、MinGit、`_probe.py`、`engine-matrix.json` |

**相对 Electron 的代价（已计入工期）**：
- 进程树、Job Object、路径编码、PTY 缓冲都要写 Rust，`node-pty` 的现成经验不可直接搬；
- 前后端类型同步需要工具（推荐 `tauri-specta` 或手工镜像 + CI 校验）；
- 生态/示例少于 Electron，出问题要读 Rust crate 源码。

**相对 Electron 的收益**：安装包 1/10、冷启动更快、内存低 100–200 MB、无 Chromium 补丁维护负担。

## 8. 许可（开源，风险显著下降）

## 9. 结论

1. 项目可行，差异化在"多实例 + 版本治理 + 依赖诊断"，不在启停本身。
2. Tauri 让体积/内存更优，代价是 Rust 侧进程与 PTY 要自己啃 → **M0 必须先做 Spike**。
3. ~~DirectML 按"锁死 torch 2.4.1 的遗产通道"设计~~ → **已放弃**；不维护一个注定无法跟随主线的引擎。
4. 唯一需要改口径的需求仍是"自动解决依赖冲突"。
5. 任务拆分、数据模型、IPC 与验收标准见 [`02-开发计划.md`](./02-开发计划.md)。
